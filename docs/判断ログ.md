# 判断ログ

設計上の判断と、その根拠を残す。後から「なぜこうなっているのか」を辿れるようにするためのもの。
**判断を変えるときは、元の記述を消さず追記する。**

書式：`## D-NN タイトル` ／ 日付・判断・理由・却下した選択肢

---

## D-01 全22機能を作らない（第1版は計算7＋参照2）

- **日付**：2026年8月3日（令和8年8月3日）
- **判断**：市販「税理Pro」の22項目を再現せず、計算7メニュー＋参照2画面に絞る
- **理由**：税制改正の保守は機能数にほぼ比例し、しかも**分岐は上書きでなく積み上げ**（過年度の試算を関与先で出すため旧ルールを消せない）。開発元がAndroid版を畳んだのも「利用者減の中で改正対応が困難」＝保守が採算に合わなくなったため。売り物でない当方は採算を考えなくてよいが、**保守できるかという壁は同じ**
- **効果**：毎年ロジックに手が入るのが「所得税エンジン」1箇所だけに集約された
- **却下**：全機能の再現（毎年どこかが未対応になる＝関与先で古い数字が出た経験を一度すると職員は二度と開かない）

## D-02 給与計算・賞与・手取から給与逆算を作らない

- **日付**：2026年8月3日
- **判断**：スコープ外
- **理由**：源泉徴収税額表＋社会保険料率で**年に複数回**更新が必要。税制改正のカレンダーとは別の時計で動き、「改正がなかった年」が存在しない。保守の重心そのもの
- **留意**：事務所が給与計算を受託しているため「この人を採用したら手取りいくら」は関与先で効くはずだが、痛みを引き受ける判断（本人決定）

## D-03 法人税の計算機を作らず、早見表で代替する

- **日付**：2026年8月3日
- **判断**：計算メニューとしては作らない。参照画面「実効税率・均等割 早見表」を置く
- **理由**：「所得×おおよそ30%」で関与先の会話は成立し、**アプリを開いて入力する時間より電卓が速い**。決算前の納税予測は事務所で試算表から正確に出すべきもので、関与先で入力し直す作業ではない
- **早見表で担保する2点**：①所得規模による率のブレ（軽減税率の区切りがあるため所得が小さい会社ほど一律30%は過大）②均等割（赤字でも発生。「今期赤字だからゼロ」が最も危険）
- **要確認**：表に載せる率・均等割は条文・告示で確定してから書く

## D-04 相続税の概算は入れる

- **日付**：2026年8月3日
- **判断**：第1版に入れる（本人決定）
- **理由**：事務所の専門領域で関与先での価値が極大。計算構造は安定していて保守は軽い
- **留意**：**財産評価額の前提ひとつで金額が大きく振れる**。職員が関与先で出した数字が確定額と受け取られないよう、評価額が入力値である旨を画面に明示する

## D-05 配り方は PWA（ネイティブアプリにしない）

- **日付**：2026年8月3日
- **判断**：PWA として配信する
- **理由**：**決め手は開発の容易さではなく「改正を即日・全員に反映できること」**。ネイティブアプリはストア審査待ちと各自の更新待ちが挟まり、**更新しない職員の端末に古い版が残る**＝事務所として同じものを見せられない。誰の端末が最新かを把握する手段もない
- **副次的な利点**：コードベース1本／Apple・Googleの年額不要／審査リジェクトなし／配布はURLを伝えるだけ
- **引き換えに設計で潰したこと**：オフライン動作（ロジックと数値表を端末にキャッシュし、オンライン時に裏で更新）

## D-06 既存の社内配り所端末を使わず GitHub Pages で公開する

- **日付**：2026年8月3日
- **判断**：GitHub Pages（`kenjio-skr.github.io/tax-pocket/`）で公開する
- **既存の配り所を使わない理由**：事務所には汎用端末1台をサーバー代わりにした社内ツールの配り所があり、kintone ポータルと DocuWorks から職員が入る（scan-to-journal が稼働中）。しかし**このツールは事務所の外で開くことが前提の初めてのツール**であり、①外部からはシン・テレワーク接続が要り「関与先で数秒」が成立しない ②運用が無管理（Windows Update の再起動で停止・起動監視なし）で関与先で開かない事故が起きる
- **既存結論との整合**：「内製費用に配り所端末を守り続ける手間を計上する」（keiei-notes 2026-07-24）に対し、本件はその手間を増やさない
- **公開でよい根拠**：顧客データを持たない設計にすれば実害は「誰でも計算機を使える」だけ。むしろ**認証を置けないことが機能要件**（関与先でログインを挟むと電卓としての速さが死ぬ）
- **公開で本当に変わるのはデータでなく対外的な見え方**：事務所名・ロゴを入れると「事務所が公開している税額計算ツール」になり、一般の人が誤った税額を得たときの責任が生じる → **事務所名・ロゴを入れず免責を1行置く**（内部ツール4原則の「ブランド配色を内部ツールに持ち込まない」とも整合）
- **他プロジェクトとの違い**：`system-ledger` / `sozoku-sim-report` / `mf-fast-entry` はローカルgit・リモート無し。**本プロジェクトが初のリモートあり・公開リポジトリ**

## D-07 数値表もリンクURLもコードに埋めない

- **日付**：2026年8月3日
- **判断**：税率表・料率・参照リンクはすべて `data/` の外部データファイルに置く
- **理由**：改正時の作業を「1ファイル差し替え」に落とすため。プログラムの知識なしに税務がわかる職員なら誰でも更新できる状態を保つ（**属人化対策**。作った人以外に改正を反映できないのは事務所のリスク）
- **効果**：PWA と組み合わせると、差し替えた瞬間に全職員へ反映される

## D-08 参照リンクはアプリ内に持つ（当初の「外部リンクで代替」から格上げ）

- **日付**：2026年8月3日
- **判断**：#21「税額表・社会保険料率等 参照」を第1版に入れる
- **当初案**：自前で持たず国税庁等のページへのリンクで足りる（＝アプリに入れない）
- **変更理由**：ブラウザを開いてお気に入りを探す摩擦が実在し、**お気に入りは職員の端末ごとにバラバラ**になる。誰かが古いページを登録したまま使い続ける事故が起きる
- **★危険なのはリンク切れではなく、古いページが正常に開くこと**：国税庁の源泉徴収税額表や協会けんぽの保険料額表は**年度ごとに別ページとして新設**されるため、去年のURLはリンクが生きていて、正しく表示され、中身だけが古い
- **対策3つ**：①URLを外部データで持つ（1ファイル差し替えで全員に反映）②各リンクに**適用年度**を表示（人が気づける形にする）③リンク集の**最終更新日**を画面下に出す
- **歯止め**：数値そのものをアプリに持つのは Rule of Three 後。先回りすると D-02 で外した給与系の保守が裏口から戻る

## D-10 リポジトリは public とする（private＋Pro を採らない）

- **日付**：2026年8月3日（令和8年8月3日）
- **判断**：`kenjiO-skr/tax-pocket` を **public リポジトリ**として作成し、GitHub Pages で配信する
- **確認した事実**：GitHub Pages は「public リポジトリなら GitHub Free、**private リポジトリからの公開は Pro / Team / Enterprise**」。また**サイト自体に認証をかける**（private publication）は Enterprise Cloud 限定（GitHub Docs）
- **理由**：private にして Pro に課金しても隠せるのは**コードとコミット履歴だけ**で、公開サイト自体は誰でも開ける。D-06 のとおり本ツールは顧問先データを持たず認証を置けないことが機能要件なので、隠すことの実益に対して費用と手間が見合わない
- **前提条件**：CLAUDE.md 冒頭の書き込み禁止ルール（顧問先名・個人名・実額・鍵・社内URL・IPアドレス）を守ること。**この前提が公開を成立させている唯一の担保**
- **却下**：private リポジトリ＋GitHub Pro／サイト自体の非公開化（Enterprise Cloud・認証を置けない機能要件と衝突）

- **副産物**：準備中ページの時点で事務所名・ロゴを入れず免責を1行置いた（設計原則5）。公開直後から対外的な見え方が要件どおりになっている

- **前提**：配布対象の職員は16人以上

## D-13 リポジトリを事務所の組織アカウントへ移管した（D-06・D-10 の公開先を変更）

- **日付**：2026年8月3日（令和8年8月3日）
- **判断**：`kenjiO-skr/tax-pocket`（個人アカウント）から **`sakurataxsys/tax-pocket`（事務所の組織アカウント）へ移管**する。公開URLは **`https://sakurataxsys.github.io/tax-pocket/`**
  - D-06・D-10・D-11 に残る `kenjio-skr.github.io/...` の記載は、判断時点の記録として消さずに残す。**以後の正はこの D-13**
- **費用**：組織アカウントは Free プランだが、**public リポジトリなら Free でも Pages が使える**ため追加費用なし
- **移した理由**：本プロジェクトが一貫して掲げる**属人化対策**（D-07「作った人以外に改正を反映できないのは事務所のリスク」）は、リポジトリが代表個人のアカウント配下にあると**権限の面で未解決のまま残る**。組織アカウントなら職員へ書き込み権限を渡せる状態を先に作れる
- **設計原則5（事務所名を入れない）との関係**：URLに事務所の識別子が入るが、**この点は決め手にならないと判断した**。移管前の `kenjio-skr` は代表個人が特定できる名前であり、公認会計士・税理士個人としての帰属を示す。**「事務所名を避けるために個人アカウントに置く」は、対外的責任（D-06）の観点では改善になっていない**。帰属を本当に消すには中立的な名前のアカウントかドメインが要るが、一般の人が辿り着く経路が実質なく免責も画面に置いてあるため、そこまでやる実益は薄い
- **★配布前に実施した理由（最重要）**：GitHub Docs に「リポジトリのWeb上のリンクとGit操作はリダイレクトされる。**しかしリポジトリに紐づく GitHub Pages はリダイレクトしない**」とある。実際、移管後に旧URLは **HTTP 404** になった（新URLは HTTP 200 を確認）
  - 配布後に移管すると、職員のホーム画面アイコンは旧URLを指したまま死に、PWA のキャッシュもオリジン単位なので**全員に手作業で追加し直してもらう**ことになる。追加し直さない職員の端末に古い版が残れば、**D-05 で PWA を選んだ理由そのものが崩れる**
  - 出典：https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository
- **書き込み権限**：当面**代表のみ**。改正対応を実際に1回回して `docs/改正対応手順.md` が埋まってから職員へ渡す（手順書がない段階で権限だけ渡しても使えないため）
- **却下**：個人アカウントのまま維持（引き継ぎ時の権限問題が残る）／独自ドメイン（DNS設定の手間に対し、現時点の実益が薄い。ただし**将来リポジトリを移してもURLが変わらない**利点があるため、配布前なら再検討の余地あり）

- **日付**：2026年8月3日（令和8年8月3日）
- **対象**：`CLAUDE.md`・`docs/仕様.md` に記載した `../keiei-notes/...` 等、事務所内の別リポジトリへの相対パス
- **判断**：**書き換えず、このまま公開する**（本人決定）

## D-15 画面構成は「単一HTML＋ハッシュルーティング」とする

- **日付**：2026年8月4日（令和8年8月4日）
- **判断**：`index.html` 1枚にすべての画面を載せ、`#/taishokukin` のようにハッシュで切り替える
- **理由**：①オフライン動作が最も確実（HTMLが1枚しかないのでキャッシュ漏れが起こりようがない）②関与先での画面遷移が瞬時 ③ホーム画面のアイコンが1つで済む
- **却下**：メニューごとに独立HTML（1メニューが壊れても他に波及せず、よく使う1つだけをホーム画面に置ける利点はあるが、**service worker の precache 一覧にページを足し忘れるとそのメニューだけオフラインで開かなくなり、しかも事務所内＝電波良好では気づけない**）
- **★引き換えに生じた副作用と、その対策**：ホーム画面から起動したPWAには**URLバーも再読込ボタンも無い**。そのため `data/*.json` を起動時に1回だけ読む実装にすると、朝アプリを開いたまま夕方の関与先で使う端末に、その日の差し替えが届かない。
  → **税率表は計算画面に入るたびに取りに行く**（`src/data.js`）。メニューへ戻って入り直せば反映される動線にした
- **確認済み**：サーバ側の `data/taishokukin.json` を書き換え、ページを再読込せずメニュー→退職金と入り直すだけで新しい値が反映されることを確認した

## D-16 キャッシュを2系統に分ける（シェル＝版付きcache-first／data＝network-first）

- **日付**：2026年8月4日
- **判断**：`sw.js` でアプリシェルと `data/*.json` を別の戦略にする

| 対象 | 戦略 | 狙い |
|---|---|---|
| アプリシェル（HTML/CSS/JS/アイコン） | 版付き cache-first（`CACHE_VERSION`） | 関与先での起動を最速にする |
| `data/*.json` | network-first（2秒で打ち切り）→ 失敗時キャッシュ | 税率表の差し替えをその場で反映する |

- **この分割が属人化対策と噛み合う**：**税務職員が `data/` を直すだけの改正は、`CACHE_VERSION` を上げる必要がなく即日反映される**（D-07）。版を上げるのはロジック改正＝開発者作業のときだけ
- **`skipWaiting()` ＋ `clients.claim()` を採用**：既定では新しい service worker は全クライアントが閉じるまで有効化されず、iOSのホーム画面アプリは長時間常駐するため「次々回の起動でようやく新版」が起こりうる。シェルを版単位でまとめて precache する設計なので、待たせずに切り替えるほうが安全
  - **副条件**：動的 `import()` を使わない。旧版のページが新版のモジュールを後から取りに行く不整合を作らないため
  - **職員から見た反映のタイミング**：`data/` の差し替え＝その場／ロジック改正＝**次回起動から**。D-12 の「知らせる経路」はこの前提で決める
- **★プリキャッシュにも `cache: "reload"` を付ける**：GitHub Pages は資産に `Cache-Control: max-age=600` を付けるため、これが無いと**版を上げて push した直後10分以内に開いた端末が「新しい版名のキャッシュに古い中身」を抱え、cache-first なので次の版まで永久に直らない**
- **実装中に見つかった不具合その1**：`data/*.json` を2本同時に取りに行くと、`caches.open()` が同時に新規作成を試みて競合し、**どちらの保存も失われてオフラインで動かなくなる**状態が再現した。キャッシュを開く約束を1つだけ持ち回す形に直して解消。保存に失敗しても取得できた内容は画面へ返すようにもした
- **★実装中に見つかった不具合その2（実運用に直結）**：**初回訪問では service worker がまだページを制御していないため、画面からの税率表の取得が service worker を通らず、キャッシュに入らない**。この状態だと「事務所で1回開いてホーム画面に追加し、そのまま電波のない関与先へ行った」端末は、画面は出るのに税率表だけ無く計算できない。**シェルと一緒に税率表も install 時に取り込む**ようにして解消（`sw.js` の `DATA_FILES`）
  - 確認：キャッシュと登録を消してから**1回だけ**開き、その後サーバを停止した状態で計算が通ることを確認した
  - 副作用：計算メニューを増やすときは `DATA_FILES` にも足す必要がある。ただしメニュー追加は開発者の作業なので、税務職員が `data/` を差し替えるだけの改正でここを触ることはない
- **`activate` で現行版以外のキャッシュを削除する**（改正のたびに旧版が端末に溜まるため）。`data` 用キャッシュには版を付けず、シェルの版を上げても残す

## D-18 減価償却費（定額法・定率法）で採った根拠と、扱わないと決めた論点

### ★償却率表は手で書き写さず、省令の別表から機械生成する

- **判断**：耐用年数省令の**別表第八・第九・第十を e-Gov 法令API v2 から取得して JSON に落とす**スクリプト（`tools/fetch_shokyakuritsu.mjs`）を作り、生成物を手で編集しない
- **理由**：3表×99行（耐用年数2〜100年）×最大3列＝約900個の数値を人が転記すると、**必ずどこかを間違え、しかも画面上はもっともらしい結果が出る**。たとえば保証率が1行ずれると「改定償却率に切り替わる年度が1年ずれる」だけなので、関与先で職員が気づく術がない
- **別表の数値は漢数字**（「〇・〇六六六」）なので変換して取り込む。耐用年数2年の定率法は改定償却率・保証率が罫線（―――――）で、これは `null` として扱う
- **要素指定（`?elm=AppdxTable_10`）は HTTP 400 で使えない**ため全文（約1.5MB）を取得して切り出している
- **取り込みミスの検知はテストで行う**（`tests/genka_shokyaku.test.js` の④）。①3表とも2〜100年が欠けなく入っている ②償却率が耐用年数に対し単調非増加 ③保証率＜償却率≦改定償却率 ④償却率が「倍率÷耐用年数」と±0.001以内

## D-20 印紙税で採った根拠と、扱わないと決めた論点

- **判断**：計算エンジンを持たず、**「作成日＋号＋記載金額」から税額を引くだけ**の画面にする。

### ★軽減表は本則より1区分少ない（実装の要。当初の計画は誤っていた）

措置法91条は「契約金額が**十万円を超えるもの**」（1項）／「**百万円を超えるもの**」（2項）だけを対象にするため、
本則の最下位区分（第1号「十万円以下のもの 二百円」・第2号「百万円以下のもの 二百円」）が**軽減表に存在しない**。

- 本則 第1号・第2号＝**11区分** ／ 軽減 1項・2項＝**10区分**
- したがって「軽減対象の文書でも、下限以下の金額と記載金額のないものは**本則へ落とす**」フォールバックが必須
- これを「同じ区分数」と思い込んでいると、生成スクリプトの検証で必ず落ちるか、建設工事請負100万円以下という
  実務で普通に出る金額で引き当てに失敗する
- **着手前の Fable 敵対的レビューで検出した**。あわせて「1,000万円ちょうどの税額」も1区分ずらして書いていた
  （正：本則1万円／軽減5千円。「五百万円を超え**千万円以下**のもの」に入る）。
  テストは各区分表の全境界を上下1円で総当たりして、この取り違えを塞いでいる

### 非課税の金額しきい値を自動適用してよい号を絞った

しきい値は生成側が非課税物件欄から機械的に取り出すが、**無条件に適用してよい号だけを allowlist する**
（`data/inshizei.json` の `非課税しきい値を適用する`）。

- **自動適用する**：第1号・第2号（契約金額1万円未満）、第3号（手形金額10万円未満）、第15号（同1万円未満）、
  第16号（配当金額3千円未満）、第17号（受取金額5万円未満）
- **自動適用しない**：第8号（「**信用金庫その他政令で定める金融機関の作成する**」預貯金証書に限られる）。
  作成者の条件が付くため、金額だけで非課税と表示すると誤る。原文を出して職員に判断させる

第17号の非課税「受取金額が五万円未満」は**号全体に係る**ので、**第17号の2（借入金・保証金の受取書など）にも及ぶ**。
第17号の2を定額200円とだけ扱うと、非課税の4万円の受取書に「200円」と表示される。

### 扱わないと決めた論点（画面に「要相談」と表示する）

1. **課税物件表の適用に関する通則1〜5**（文書の所属の決定、2以上の号に該当する場合、記載金額の計算、
   契約金額を変更する契約書、外国通貨の換算＝**通則4ヘ**）。**どの号に当たるかの判定は職員の仕事**と画面で断る
   - 通則は**5まである**（4までではない）。通則5（念書・請書その他一方のみが作成する文書も「契約書」に含む。
     第1・2・7・12〜15号）は関与先で頻出するため、扱わないものではなく**注記に載せた**
2. **消費税額等が区分記載されている場合の記載金額**（第1号・第2号・第17号）。計算には入れず、金額欄の直下に注記を置く
   - ⚠️ 二次情報：国税庁タックスアンサー No.7124（https://www.nta.go.jp/taxes/shiraberu/taxanswer/inshi/7124.htm ）。
     信頼度＝高（政府系）。個別通達（平元.3.10 間消3-2）の原文は MCP の対象外で未取得
3. 印紙税法5条2号・3号の非課税（国・地方公共団体・別表第二・第三の者が作成した文書）
4. **措置法91条の2**（自然災害の被災者が作成する代替建物の取得等に係る不動産譲渡契約書等の非課税）
5. **第17号の「営業に関しない受取書」**。法人形態・出資者との関係で決まり機械判定できない。
   第17号を選んだときに1行の注意を出す

## D-21 延滞税・利子税で採った根拠と、扱わないと決めた論点

- **日付**：2026年8月4日（令和8年8月4日）
- **判断**：割合は**年ごとの数値をそのまま持ち、式で導かない**。生成スクリプトは作らない

### 採った根拠（すべて原文を取得して確認）

| 論点 | 根拠 | 内容 |

### ★利子税の割合は令和2年度改正で式が変わっている（当初の計画は誤っていた）

当初は「平均貸付割合を年に1つだけ持ち、3つの割合を条文の式から導く」設計にしていた。これは誤り。

- **令和2年分まで**（平成31年6月1日時点の措法93条2項を e-Gov の時点指定で取得して確認）：
  利子税＝**特例基準割合**＝「財務大臣が告示する割合に、年**一パーセント**の割合を加算した割合」
- **令和3年分から**（現行の措法93条2項）：
  利子税＝**利子税特例基準割合**＝「平均貸付割合…に年**〇・五パーセント**の割合を加算した割合」

現行の式を全年に当てると、**平成26年分〜令和2年分の7年分がすべて0.5ポイント低く出る**（平成26年なら
正 1.9% に対し 1.4%）。しかも延滞税の割合は両方の時期で「＋1%」「＋7.3%」のまま変わらないため、
延滞税だけを公表値と突き合わせるテストは全年グリーンになり、**利子税の誤りだけがすり抜ける**。

過年度の試算（修正申告のやり直し）を関与先で出すのが本プロジェクトの要件であり、
`data/CLAUDE.md`「改正は上書きせず、版を足す」にも反する。**着手前の Fable 敵対的レビューで検出した。**

対応：式で導くのをやめ、**年ごとの3つの割合をそのまま `data/entaizei.json` に持つ**。
テストで①全年の延滞税の割合が国税庁公表値と一致すること ②2つの割合の差が常に6.3ポイントであること
③利子税の出典区分が令和2年分まで「公表」・令和3年分以後「条文から算出」に分かれていること、を固定した。

### 年別の割合の出所（一次・二次の区別）

- 割合の**決め方**（措法93条・94条・96条、通則法60条・118条・119条・10条）は**すべて原文を取得**
- 年別の**数値**は ⚠️ **二次情報**：国税庁「延滞税の割合」
  https://www.nta.go.jp/taxes/nozei/entaizei/keisan/entai_wariai.htm 信頼度＝高（政府系）。
  元の平均貸付割合は**財務大臣告示**で、e-Gov の法令DBには収録されていない（利用者判断で二次情報を採用）
- 令和3年分以後の**利子税**の数値は、国税庁公表の延滞税の割合から措法93条2項・94条1項の式で
  **算出した値**で、公表値そのものの引き写しではない。`data/entaizei.json` の各年に出典区分として明記し、
  原典での確認を `TASKS.md` に残した

### 扱わないと決めた論点（画面に明示する）

1. **通則法61条の期間の特例**（期限内申告から1年経過後の修正申告等で一定期間を控除するもの）。
   ただし**該当しうる入力を検知して警告を出す**（法定納期限から1年超で提出した修正申告）。
   黙って過大な額を出さないため
2. 通則法62条（一部納付）、63条（納税の猶予等の場合の免除）
3. 偽りその他不正の行為により国税を免れた場合（61条の1年の特例が働かない）
4. 加算税そのもの
5. 相続税の延納・物納に係る利子税（措法93条3項。分納期間ごとの延納特例基準割合で決まる別計算）
6. 地方税の延滞金（割合も根拠条文も国税とは別）
7. 納期限が日曜・祝日に当たる場合の期限の特例（通則法10条2項）
8. **平成25年12月31日以前**の期間（特例基準割合方式が始まる前）

### 「納期限」と「法定納期限」を別の入力にした

通則法60条2項は、日数の起算を**法定納期限**、低い割合の終期を**納期限**の翌日から2月と定めており、
期限後申告・修正申告では納期限＝提出日になる（両者が一致するのは期限内申告のみ）。
画面に「申告の区分」を置き、期限後・修正のときだけ提出日を入力させる。

### 生成スクリプトを作らなかった理由

取り込む数値が年あたり3つしかなく、しかも出所が法令DBではなく国税庁のページであるため、
自動生成の器を作っても得るものがない（Rule of Three・単純さ最優先）。
その代わり、年次更新の書き写しミスは上記3本のテストで捕まえる。

### 端数処理の順序

1. 課税標準 … 千円未満切捨て（通則法118条1項）→ 全額が千円未満なら千円（登免法15条）
2. 税額 … 課税標準 × 税率 の百円未満切捨て（通則法119条1項）
3. 別表の但書の最低税額（15万・6万・3万）まで引き上げ
4. なお千円未満なら千円（登免法19条）

3と4はどちらも千円単位の下限なので、2と入れ替えても結果は変わらない（最低税額がすべて100円の倍数のため）。
念のためテストで固定した。

### 収録開始日を令和4年9月1日にした理由（機械的に確認した）

e-Gov の法令XMLは最新版しか返さないため、「現行の表が過去に遡って正しい」は仮定にすぎない。
時点指定（`asof`）で**二分探索**し、第1号・第24号の全行が現行と一致する最古の日を求めた結果、
**2022-09-01（令和4年9月1日）** で切り替わっていた。会社法改正による**支店の所在地における登記の廃止**の施行日で、
それ以前の第24号には「支店又は従たる事務所の所在地においてする登記」の区分（一件9,000円など）があった。
第1号側も令和2年4月1日の配偶者居住権の追加で構成が変わっている。

措置法4条文の**税率**は 2022-09-01 以降で変わっておらず（延長されているのは期限だけ）、
適用開始日も動いていないことを同じ方法で確認した。

なお `asof` は 2017-04-01 より前を受け付けない（API が 400 を返す）ため、この方法で遡れるのはそこまで。

### 税率表は別表第一と措置法から自動生成する（`tools/fetch_toroku_menkyozei.mjs`）

減価償却（D-18）・印紙税（D-20）と同じ理由。人が69件を転記すれば必ずどこかを間違え、
しかも画面にはもっともらしい結果が出る。**生成物（`data/toroku_menkyozei_hyo.json`）は手で編集しない。**

印紙税のパーサをそのまま流用できなかった点：

- **中黒つきの小数**がある（「千分の一・五」）。整数の分子・分母（15/10000）に落とし、浮動小数を作らない
- 階層が `（一）` → `イ` → `（１）` の**3段**で、しかも `（三の二）` のような枝番がある。
  番号は意味を取らずラベルとして持つ
- 但書が「第1列が空・第2列 `colspan="2"`」の**継続行**として入る（第1号に1件・第24号に7件）
- 号の境界は**見出し行（1セルの行）で検出**する。行番号を焼き込むと、改正で行が増減したときに
  隣の号が混入する

### 着手前の敵対的レビュー（別コンテキスト）で潰したもの

前回セッションのレビューで出た致命3件に加え、今回のレビューで次を直した。指摘は原文と実測で検証してから採った。

1. **措法73条の「売買その他の政令で定める原因」は法律本文の限定**であって政令要件ではない。

   選択肢の文言に「売買等により取得した」を入れ、補足に贈与・相続・交換が対象外であることを書いた
2. **措法72条1項2号（土地の所有権の信託 千分の三）の紐づけ先が抜けていた**。

3. **第24号（一）カの「一般社団法人等」は資本金と無関係に括弧書きの税額**。

指摘のうち2件は採らなかった。行番号のずれ（1件）は0起点と1起点の数え方の違いで、実測すると誤りではなかった。

### 軽減を別表の行に直付けしなかった

別表の `（二）ハ その他の原因による移転の登記` は、**土地も建物も、売買も贈与も1行**にまとめている。
`（五）` も抵当権の設定から差押え・仮処分まで1行。ここに軽減を直付けすると、
本来当たらない登記に軽減が当たる経路が開く。

そこで軽減は**相互排他のセレクト**にし、既定を「なし」にした。文言に対象（土地／売買／住宅用家屋）を書き、
選ばない限り本則で計算する。（二）ハには72条1項1号と73条の2つが並ぶ。

### 適用期間をどの日で判定するかは条文で違う

- 措法72条 …「その間に…**登記を受ける**場合」→ 登記を受ける日
- 措法72条の2・73条・75条 …「その間に…**新築し、又は…取得し**」→ 新築・取得の日
  （加えて「取得後1年以内に登記を受けるものに限り」）

機械で読み分けられないため、`data/toroku_menkyozei.json` に人が書く。
画面は住宅用家屋系の軽減を選んだときだけ「新築・取得した日」の欄を出し、
登記日がその1年後を過ぎていたら警告を出す（政令のやむを得ない事情があるため止めはしない）。

### 扱わないと決めた論点（画面に明示する）

1. 第1号・第24号以外の号
2. **第24号（一）ホ・ヘ**（新設合併・組織変更・種類の変更による設立／吸収合併による増資）。
   「千分の一・五（…**財務省令で定めるもの**を超える資本金の額に対応する部分については、千分の七）」の
   二段税率で、区切りが財務省令に委ねられている。委任先を確認していないので計算しない。
   選んだら理由と税率欄の原文を出す（黙って隠すと「無い」と誤解される）。

4. **登免法17条1項**（仮登記に基づく本登記の税率控除）・**17条4項**（借地権者等の底地取得で2分の1）
5. 非課税・免税の各規定。ただし `第1号（二）イ`（相続）には**措法84条の2の2**
   （価額100万円以下の土地の相続登記の免税）の1行注記を置く。過大に出るのを止めるため
6. 不動産の価額そのものの算定（持分・共有・附則7条の政令の価額）
7. 同一の申請書で複数の登記を受ける場合の合算、登免法13条（共同担保）等の特例

### 第1号（十五）の但書は「最低税額」ではない

「（同一の申請書により二十個を超える不動産について登記の抹消を受ける場合には、申請件数一件につき二万円）」は
下限ではなく**別建ての額**。最低税額の但書と同じ扱いにすると、21個で21,000円と過大に出る（正しくは20,000円）。
生成物では但書を種別で分け、計算では置き換えている。

この画面は定額課税を**申請書1件分**として計算するため、個数が20を超えたら但書を自動で適用する
（「同一の申請書による」のチェック欄は置かない。外し忘れが過大な税額に直結するため）。

## D-23 リンク集に載せるものと、載せ方

日付：2026年8月5日（令和8年8月5日）

13件を4分類（源泉徴収・給与／社会保険・労働保険／資産税・評価／そのほか）で `data/link_shu.json` に置いた。

### 全URLを実際に取得して確認した

記憶でURLを書かず、13件すべてに HTTP リクエストを投げて 200 を確認し、
年度が入るものは検索で最新年度のページを特定してから採った。

### 適用年度は名称の右に、同じ行で出す

設計原則6のとおり。**危ないのはリンク切れではなく、古いページが正常に開くこと。**
年度が名称と同じ大きさで隣にあれば、開く前に気づける。補足文の中に埋めない。

令和8年分がまだ公開されていないもの（年末調整のしかた・法定調書の手引）は、
**令和7年分のリンクに「令和7年分」と表示して載せた**。隠すより、古いと見えている方が安全。

### 協会けんぽは都道府県別の一覧ページへリンクする

設計原則5（事務所名・ロゴを入れない）と同じ理由で、一覧ページに留めて職員に1タップ選ばせる。

### 自前の計算メニューと重なるものも、あえて残した

印紙税の手引・耐用年数表は、このツールに計算メニューがある。それでも載せたのは、
**号の判定や資産の区分は人が原典で確かめるもの**で、税額の引き当てとは別の作業だから。
補足に「税額そのものはこのツールのメニューに入っています」と書いて役割を分けた。

## D-24 法人税の早見表で採った根拠と、扱わないと決めた論点

日付：2026年8月5日（令和8年8月5日）

### 計算機は作らず、掛け算で出ない2点だけを担保する

`docs/仕様.md` §3 のとおり。所得を入力させず、`data/hojinzei_hayami.json` の
「所得規模の行」（7段階）について表を組むだけにした。**入力は事業年度開始日1つ**。

### 根拠条文（すべて e-Gov 法令API v2 で原文を取得）

| 税目 | 根拠 | 率 |
|---|---|---|
| 法人税（本則） | 法人税法66条1項 | 「百分の二十三・二」 |
| 法人税（中小の年800万円以下） | 法人税法66条2項 | 「百分の十九」 |
| 同（軽減の特例） | 措法42条の3の2第1項1号 | 「百分の十五（所得の金額が年十億円を超える事業年度については、百分の十七）」。令和9年3月31日までに開始する事業年度 |
| 地方法人税 | 地方法人税法10条1項 | 「百分の十・三」 |
| 住民税 法人税割 | 地方税法51条1項・314条の4第1項 | 標準 道府県1%・市町村6%（制限 2%・8.4%） |
| 事業税 所得割 | 地方税法72条の24の7第1項3号 | 3.5 / 5.3 / 7.0%（400万・800万の区切り） |
| 特別法人事業税 | 特別法人事業税法7条3号 | 基準法人所得割額に「百分の三十七」 |
| 均等割 | 地方税法52条1項・312条1項 | 道府県5区分・市町村9区分 |

### 17%は「年800万円以下の部分」にだけ掛かる

措法42条の3の2は、法人税法66条2項の「百分の十九」という**税率そのものを置き換える**形で書かれている。
したがって所得10億円超の事業年度でも、17%が掛かるのは年800万円以下の部分だけで、
800万円を超える部分は本則23.2%のまま。所得全体に17%と読むと大きく外れる。

### 収録開始日を令和7年4月1日にした（機械的に確認した）

e-Gov の時点指定（`asof`）で二分探索し、**17%が条文に入ったのが 2025-04-01**（2025-03-31 時点には無い）
であることを確認した。あわせて、ほかの8条文の率が 2025-04-01 から現在まで変わっていないことも確認した。
それより前に開始する事業年度は表を組まない。

※ 確定作業の途中で e-Gov API が **HTTP 200 のままエラーHTMLを返す**状態になり、
一度は誤った結果（全条文が「不一致」）が出た。以後、レスポンスに `<ArticleTitle>` が
含まれることを確認してから採用するようにした。**連続アクセスは条文ごとに間隔を空ける。**

### 法定実効税率の式は、特別法人事業税も損金算入する

```
(法人税率 × (1 + 地方法人税率 + 住民税法人税割率) + 事業税率 × (1 + 特別法人事業税率))
  ÷ (1 + 事業税率 × (1 + 特別法人事業税率))
= (0.232 × 1.173 + 0.07 × 1.37) ÷ (1 + 0.07 × 1.37) ≒ 33.58%
```

分母の事業税率に `(1 + 特別法人事業税率)` を掛け忘れると34%台になり、約0.8ポイント高く出る。
テストで33.58%を固定し、掛け忘れた式が34%を超えることも併せて確認している。

### 着手前の敵対的レビュー（別コンテキスト）で潰したもの

率そのものに誤りは無かったが、**「対象の線引き」と「時間軸」**に穴があった。
指摘はすべて条文で裏を取ってから採った。

1. **収録開始日のガードが無かった**（上記のとおり追加）
2. **大法人の100%子法人等**（法人税法66条5項）。資本金1億円以下でも19%も15%も使えず全額23.2%。
   「大法人（資本金5億円以上等）との間に完全支配関係がある普通法人」で、関与先で出る類型
3. **3以上の道府県に事務所を設ける資本金1,000万円以上の法人**（地方税法72条の24の7**第5項**）。
   事業税の400万・800万の区切りが使えず所得全額に7%
4. **資本金1億円以下でも外形標準課税の対象になる場合がある**（地方税法72条の2第1項1号ロ。
   払込資本50億円超の特定法人の100%子法人で払込資本2億円超など。令和6年度改正）
5. **均等割の区分は「資本金等の額」と「資本金＋資本準備金の合算額」の大きい方**で決まる
   （地方税法52条4項・312条6項）。資本金等の額だけで引くと1つ下の区分になる
6. **市町村の従業者数は「その市町村内の」事務所等の従業者数**（312条1項1号ホ）。全社の人数ではない
7. **特別法人事業税は超過課税の自治体でも標準税率ベース**（同法2条5号の基準法人所得割額）。
   事業税だけ実額に置き換えて37%側まで増やす誤用を防ぐ注記を入れた
8. 軽減の期限切れ後は、黙って19%に戻さず**警告を1行出す**（D-20 と同じ作法）

2〜6はいずれも判定を実装せず、**画面の「扱わないもの」と「均等割の区分の見かた」に明記**した。
早見表に判定を持ち込むと入力が増え、「計算機を作らない」という第1版の判断が崩れるため。

### 特定の自治体の率は載せない

住民税の法人税割と均等割には自治体ごとの超過課税がある。実務では所在地の率が要るが、
特定の自治体を載せると**公開リポジトリから事務所の所在地が読み取れる**（設計原則5）。
すべて標準税率とし、実額は各自治体で確認させる。リンク集で協会けんぽを都道府県別一覧に
留めたのと同じ理由（D-23）。
