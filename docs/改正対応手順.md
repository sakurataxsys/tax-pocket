# 改正対応手順

> **作業手順の本体はまだ空です。**
> 1回目の改正対応を実際に回したときに、やった作業をそのまま書き起こして埋めます。
> 先回りして書いた手順は外れるので、書きません（`.claude/skills/` へのスキル化も1回目の後）。
>
> ただし「職員への知らせ方」と「`data/` を直すだけでは済まないもの」は、
> **やってみないと分からないことではなく、すでに決めたこと**なので先に書いてあります。

---

## 埋めるときの観点（骨子）

### 1. 年間カレンダー

改正対応が必要な時期は**すべて事務所の繁忙期と重なる**。いつ何が来るかを先に一覧にする。

| 時期 | 何が動くか | 触るファイル |
|---|---|---|
| 12月 | 税制改正大綱 | （影響範囲の確認のみ） |
| 3月末 | 法案成立 | |
| 4月 / 1月 | 施行 | |
| 毎年 | 延滞税・利子税の割合 | `data/` |
| 毎年 | 源泉徴収税額表・社会保険料率のページ更新 | `data/` のリンク集 |

### 2. 作業手順

- どのファイルを、どう直すか
- 旧年度のデータを**消さずに**版を足す方法
- 出典（法令・告示・公表資料）の記載場所

### 3. 確認手順

- テストの走らせ方（端数処理・境界値・改正前後の分岐）
- 反映後に画面で見る箇所（適用年度の表示・リンク集の最終更新日）
- 公開されたことの確認方法

### 4. 引き継ぎの観点

**この手順書の目的は、代表以外の職員が改正対応できる状態を作ること。**
プログラムの知識を前提にした書き方をしない。

## 職員への知らせ方（決定済み。1回目を待たずに書く）

改正を反映したら **チャットワークの「税額ポケット」グループに投稿する**（判断ログ D-12・D-25）。
職員は投稿とアプリの「更新の確認」画面を見比べて、自分の端末が反映済みかを判断する。

### ★投稿に書く日付は「投稿した日」ではない

**差し替えた JSON に書いた日付そのもの**（＝「更新の確認」画面に出る日付）を書く。
ここを取り違えると、職員の画面と永久に一致せず、**全員が「反映されていない」と誤解する**。

### 文例：数値表だけを差し替えたとき（`data/` の差し替え）

```
【税額ポケット】数値表を更新しました

・延滞税・利子税の割合 → 2027年1月5日
（令和9年分の割合を追加しました）

確認のしかた
メニュー →「更新の確認」→ 上の行と同じ日付が出ていれば反映済みです。
古いままなら、通信できる場所でもう一度「更新の確認」を開いてください。
```

### 文例：計算のしかたを直したとき（`src/` の変更＝版が上がる）

```
【税額ポケット】計算のしかたを直しました

・アプリの版：v11
・（直した内容を1行で）

確認のしかた
アプリをいったん閉じて開き直してから、
メニュー →「更新の確認」→ 一番上の版が v11 になっていれば反映済みです。
```

- **版が上がる改正では、必ず「閉じて開き直す」を書く。** ロジックは版付き cache-first のため、
  開いたままでは切り替わらない（判断ログ D-16）
- 数値表と版の両方が動いた改正では、**両方を別々の行に書く**（片方だけ反映されている状態が実在するため）
- **メニューに「更新の確認」が無い端末は古いまま。** 職員がそう申告してきたら、閉じて開き直してもらう

## 先に分かっている例外：`data/` を直すだけでは済まないもの

原則は「`data/` のファイルを差し替えれば、その日のうちに全職員の端末へ反映される」。
ただし次のものは**開発者の作業が要る**。1回目の改正対応を回すときに、ここも一緒に手順化する。

### 印紙税額表（`data/inshizei_hyo.json`）は編集せず再生成する

条文から機械的に作っているため、手で直さない（判断ログ D-20）。

```
node tools/fetch_inshizei.mjs
npm test
```

### 軽減措置が延長されたとき（令和9年3月31日期限）

不動産譲渡契約書・建設工事請負契約書の軽減（措置法91条）は **令和9年3月31日まで**。
延長されると、上の再生成だけでは**テストが落ちたままになる**。

- 落ちるのは `tests/inshizei.test.js` の「軽減措置の適用終了日が令和9年3月31日である」
- これは**わざと落ちるようにしてある**。期限が動いたことを人に気づかせるための仕掛け
- 復旧手順：①`node tools/fetch_inshizei.mjs` で再生成 ②テストに書いてある `"2027-03-31"` を新しい期限に書き直す
- **②はテストファイルの編集なので開発者の作業**

延長されなかった場合は何もしなくてよい。期限を過ぎた作成日を入れると、
画面が自動的に本則で計算し、警告を1行出す。

### 登録免許税額表（`data/toroku_menkyozei_hyo.json`）も編集せず再生成する

条文から機械的に作っているため、手で直さない（判断ログ D-22）。

```
node tools/fetch_toroku_menkyozei.mjs
npm test
```

**別表第一の構成が変わったときは、再生成が例外で止まる**（葉・見出し・但書の件数を検査しているため）。
これはわざとそうしてある。止まったら原文を確認し、`tools/fetch_toroku_menkyozei.mjs` の `KOZO` の
件数を直してから、画面の文言（`data/toroku_menkyozei.json` の軽減の紐づけ・葉ごとの注意）を見直す。

軽減の期限（措法72条＝令和11年3月31日／72条の2・73条・75条＝令和9年3月31日）が延長されたときは、
再生成するだけでよい（期限をテストに焼いていないため）。延長されなければ何もしなくてよく、
期限後の日付を入れると画面が自動的に本則で計算して警告を1行出す。

★**登記の種類が増減したときは、施行日より前の日付で古い税額が出ないかを確認する。**
`data/toroku_menkyozei.json` の `収録開始日` は「現行の表が遡って有効な最古の日」であり、
構成が変わったら繰り上げる必要がある。確認は e-Gov の時点指定（`asof`）で行う（D-22 に手順あり）。

### 延滞税・利子税の割合を毎年足すとき（`data/entaizei.json`）

**このツールで唯一、毎年必ず触るファイル。** 国税庁「延滞税の割合」
https://www.nta.go.jp/taxes/nozei/entaizei/keisan/entai_wariai.htm から新しい年の3つの割合を足す。

```json
{ "適用年": 2027, "適用年表示": "令和9年",
  "延滞税_納期限の翌日から2月以内": 0.0,
  "延滞税_2月を経過した日以後": 0.0,
  "利子税": 0.0,
  "利子税の出典区分": "条文から算出" }
```

- **既存の年を書き換えない。新しい年を足すだけ**（過年度の試算に使うため）
- 延滞税の2つの割合は、差が必ず**6.3ポイント**になる（措置法94条1項）。ならなければ書き写しを間違えている
- 利子税は「延滞税の2月以内の割合 − 1.5ポイント」（令和3年分以後の式。措置法93条2項）
- **`npm test` を必ず走らせる。** テストに新しい年の公表値を1行足す作業（開発者作業）が伴う
  → `tests/entaizei.test.js` の「国税庁が公表している延滞税の割合と一致する」の表
