# 改正対応手順

> **作業手順の本体はまだ空です。**
> 1回目の改正対応を実際に回したときに、やった作業をそのまま書き起こして埋めます。
> 先回りして書いた手順は外れるので、書きません（`.claude/skills/` へのスキル化も1回目の後）。
>
> ただし「職員への知らせ方」と「`data/` を直すだけでは済まないもの」は、
> **やってみないと分からないことではなく、すでに決めたこと**なので先に書いてあります。

---

## 埋めるときの観点（骨子）

### 1. 年間カレンダー

改正対応が必要な時期は**すべて事務所の繁忙期と重なる**。いつ何が来るかを先に一覧にする。

| 時期 | 何が動くか | 触るファイル |
|---|---|---|
| 12月 | 税制改正大綱 | （影響範囲の確認のみ） |
| 3月末 | 法案成立 | |
| 4月 / 1月 | 施行 | |
| 毎年 | 延滞税・利子税の割合 | `data/` |
| 毎年 | 源泉徴収税額表・社会保険料率のページ更新 | `data/` のリンク集 |

### 2. 作業手順

- どのファイルを、どう直すか
- 旧年度のデータを**消さずに**版を足す方法
- 出典（法令・告示・公表資料）の記載場所

### 3. 確認手順

- テストの走らせ方（端数処理・境界値・改正前後の分岐）
- 反映後に画面で見る箇所（適用年度の表示・リンク集の最終更新日）
- 公開されたことの確認方法

### 4. 引き継ぎの観点

**この手順書の目的は、代表以外の職員が改正対応できる状態を作ること。**
プログラムの知識を前提にした書き方をしない。

## 職員への知らせ方（決定済み。1回目を待たずに書く）

改正を反映したら **チャットワークの「税額ポケット」グループに投稿する**（判断ログ D-12・D-25）。
職員は投稿とアプリの「更新の確認」画面を見比べて、自分の端末が反映済みかを判断する。

### ★投稿に書く日付は「投稿した日」ではない

**差し替えた JSON に書いた日付そのもの**（＝「更新の確認」画面に出る日付）を書く。
ここを取り違えると、職員の画面と永久に一致せず、**全員が「反映されていない」と誤解する**。

### 文例：数値表だけを差し替えたとき（`data/` の差し替え）

```
【税額ポケット】数値表を更新しました

・延滞税・利子税の割合 → 2027年1月5日
（令和9年分の割合を追加しました）

確認のしかた
メニュー →「更新の確認」→ 上の行と同じ日付が出ていれば反映済みです。
古いままなら、通信できる場所でもう一度「更新の確認」を開いてください。
```

### 文例：計算のしかたを直したとき（`src/` の変更＝版が上がる）

```
【税額ポケット】計算のしかたを直しました

・アプリの版：v11
・（直した内容を1行で）

確認のしかた
アプリをいったん閉じて開き直してから、
メニュー →「更新の確認」→ 一番上の版が v11 になっていれば反映済みです。
```

- **版が上がる改正では、必ず「閉じて開き直す」を書く。** ロジックは版付き cache-first のため、
  開いたままでは切り替わらない（判断ログ D-16）
- 数値表と版の両方が動いた改正では、**両方を別々の行に書く**（片方だけ反映されている状態が実在するため）
- **メニューに「更新の確認」が無い端末は古いまま。** 職員がそう申告してきたら、閉じて開き直してもらう

## 先に分かっている例外：`data/` を直すだけでは済まないもの

原則は「`data/` のファイルを差し替えれば、その日のうちに全職員の端末へ反映される」。
ただし次のものは**開発者の作業が要る**。1回目の改正対応を回すときに、ここも一緒に手順化する。

### 印紙税額表（`data/inshizei_hyo.json`）は編集せず再生成する

条文から機械的に作っているため、手で直さない（判断ログ D-20）。

```
node tools/fetch_inshizei.mjs
npm test
```

### 軽減措置が延長されたとき（令和9年3月31日期限）

不動産譲渡契約書・建設工事請負契約書の軽減（措置法91条）は **令和9年3月31日まで**。
延長されると、上の再生成だけでは**テストが落ちたままになる**。

- 落ちるのは `tests/inshizei.test.js` の「軽減措置の適用終了日が令和9年3月31日である」
- これは**わざと落ちるようにしてある**。期限が動いたことを人に気づかせるための仕掛け
- 復旧手順：①`node tools/fetch_inshizei.mjs` で再生成 ②テストに書いてある `"2027-03-31"` を新しい期限に書き直す
- **②はテストファイルの編集なので開発者の作業**

延長されなかった場合は何もしなくてよい。期限を過ぎた作成日を入れると、
画面が自動的に本則で計算し、警告を1行出す。

### 登録免許税額表（`data/toroku_menkyozei_hyo.json`）も編集せず再生成する

条文から機械的に作っているため、手で直さない（判断ログ D-22）。

```
node tools/fetch_toroku_menkyozei.mjs
npm test
```

**別表第一の構成が変わったときは、再生成が例外で止まる**（葉・見出し・但書の件数を検査しているため）。
これはわざとそうしてある。止まったら原文を確認し、`tools/fetch_toroku_menkyozei.mjs` の `KOZO` の
件数を直してから、画面の文言（`data/toroku_menkyozei.json` の軽減の紐づけ・葉ごとの注意）を見直す。

軽減の期限（措法72条＝令和11年3月31日／72条の2・73条・75条＝令和9年3月31日）が延長されたときは、
再生成するだけでよい（期限をテストに焼いていないため）。延長されなければ何もしなくてよく、
期限後の日付を入れると画面が自動的に本則で計算して警告を1行出す。

★**登記の種類が増減したときは、施行日より前の日付で古い税額が出ないかを確認する。**
`data/toroku_menkyozei.json` の `収録開始日` は「現行の表が遡って有効な最古の日」であり、
構成が変わったら繰り上げる必要がある。確認は e-Gov の時点指定（`asof`）で行う（D-22 に手順あり）。

### 延滞税・利子税の割合を毎年足すとき（`data/entaizei.json`）

**このツールで唯一、毎年必ず触るファイル。** 国税庁「延滞税の割合」
https://www.nta.go.jp/taxes/nozei/entaizei/keisan/entai_wariai.htm から新しい年の3つの割合を足す。

```json
{ "適用年": 2027, "適用年表示": "令和9年",
  "延滞税_納期限の翌日から2月以内": 0.0,
  "延滞税_2月を経過した日以後": 0.0,
  "利子税": 0.0,
  "利子税の出典区分": "条文から算出" }
```

- **既存の年を書き換えない。新しい年を足すだけ**（過年度の試算に使うため）
- 延滞税の2つの割合は、差が必ず**6.3ポイント**になる（措置法94条1項）。ならなければ書き写しを間違えている
- 利子税は「延滞税の2月以内の割合 − 1.5ポイント」（令和3年分以後の式。措置法93条2項）
- **`npm test` を必ず走らせる。** テストに新しい年の公表値を1行足す作業（開発者作業）が伴う
  → `tests/entaizei.test.js` の「国税庁が公表している延滞税の割合と一致する」の表

### ★条文を取る前に：未施行の改正を必ず見る（これを飛ばして1度外している）

**「e-Gov の現行施行版」＝「いま試算する年分に適用される版」ではない。**
所得税の年分改正は、**その年の12月1日に施行して当年分から適用する**のが通例である。
つまり8月に現行施行版だけを見ると、**その年分に本当に適用される条文を丸ごと見落とす。**

実際に令和8年度改正（令和8年法律第12号・第2号。2026年3月31日公布／施行は2026年12月1日・2027年1月1日）
を取りこぼし、給与所得控除・基礎控除・扶養親族等の所得要件が令和8年分について誤ったまま入っていた
（判断ログ D-28）。**条文を取るときは、必ずリビジョン一覧から先に見る。**

```
curl "https://laws.e-gov.go.jp/api/2/law_revisions/340AC0000000033"   # 所得税法
curl "https://laws.e-gov.go.jp/api/2/law_revisions/325AC0000000226"   # 地方税法
curl "https://laws.e-gov.go.jp/api/2/law_revisions/332AC0000000026"   # 租税特別措置法
```

`amendment_enforcement_date` が**今日より先**のものが改正の予告である。年分で引く税目は
**「その年の12月31日までに施行される最後の版」**を使い、そのリビジョンIDを条文取得に渡す。

```
curl "https://laws.e-gov.go.jp/api/2/law_data/<リビジョンID>?law_full_text_format=json&elm=Article_86"
```

**適用年分は本文からは分からない。** 必ず改正法の附則（経過措置）で
「令和○年分以後の所得税について適用し」「令和○年度以後の年度分の個人の道府県民税について適用し」
を読む。読んだ条を `data/*.json` の `出典` に書き残す。

### 所得税エンジン（`data/shotokuzei.json`・`data/juminzei.json`・`data/bunri_kazei.json`）

**このツールで毎年ロジックに手が入りうる唯一の場所**（第1版設計の要。`docs/仕様.md` §2）。
基礎控除・給与所得控除は近年の改正で実際に動いている。詳しい根拠は判断ログ D-27・**D-28**。

**版を足したら、必ず別表第五を原文と全行照合する。**

```
node tools/verify_besshi5.mjs        # 収録している全年分
node tools/verify_besshi5.mjs 2026   # その年分だけ
```

**`data/` を直すだけで済むもの**：控除額・税率・しきい値の数値、版の追加。

**開発者の作業が要るもの**：

- **別表第五の刻みや区切りが変わったとき**。`data/shotokuzei.json` は表を持たず、
  しきい値と刻み（4,000）から再現している。構造が変わったら
  `src/calc/shotokuzei.js` の `calc_kyuyo_shotoku` に手が入る。
  ★**別表第五には不規則な区分が現れる。**令和6年分以前は 1,619,000〜1,628,000 に幅1,000円・2,000円の行、
  令和8年分は刻みの開始が 2,026,000（4,000の倍数でない）で最初の1区分だけ幅2,000円。
  数値だけでなく構造の違いを入れること。**`node tools/verify_besshi5.mjs` が全行を検査する**ので、
  版を足したら必ず走らせる
- **人的控除の項目が増減したとき**。`data/shotokuzei.json` の `人的控除`・`data/juminzei.json` の
  `所得控除`・同 `調整控除.人的控除差額表` の**3箇所を対で直す**（テストがキーの一致を検査している）。
  なお、新設された控除が地方税法37条1号イの人的控除差額表に入るとは限らない
  （特定親族特別控除は入っていない。D-27）
- **住民税の年度と年分**：`data/juminzei.json` の版は**所得の年分**で持つ。改正の告知は
  「令和○年度分以後」と書かれるので、**年度 − 1 = 年分**に読み替えてから版を足す

### 租税特別措置法の原文が e-Gov で取れないとき（404）

措置法は**最新版だけ本文ファイルが未生成**のことがあり、tax-law MCP や `law_data` の単純な取得が
404 になる。MCP の不具合ではないので、次の手順で1つ前の施行版から条文だけを取る。

```
curl "https://laws.e-gov.go.jp/api/2/law_revisions/332AC0000000026"
curl "https://laws.e-gov.go.jp/api/2/law_data/<リビジョンID>?law_full_text_format=json&elm=Article_41_16_2"
```

- `elm` は条番号の「の」を `_` にする（41条の16の2 → `Article_41_16_2`）
- `asof=YYYY-MM-DD` を付けると時点指定で取れる（改正前後の分岐を確かめるときに使う）
- 地方税法（`325AC0000000226`）は全文が約12MB。ダウンロードしてローカルで検索するほうが速い
